# Rust design and delivery quality

Passing tests is necessary, not sufficient. Reviewers of earlier migrations
commented mostly on design, types, tests and delivery shape, not on correctness.
Apply this during planning and again before handoff; it complements the
[compatibility checklist](compatibility.md), which covers behavior.

## Design for the next Rust consumer

- Before choosing an API, find the code that will call it next, including Rust
  callers planned or already present, not only today's C callers. Record which
  abstractions they already use (for example `std::io` traits, cursors,
  existing error types) and either adopt them or provide a thin adapter.
- When no C caller is switched in this scope, the Rust-side consumer is the
  design constraint. Do not invent a slice/pointer API that the consumer would
  immediately wrap.
- Public error types implement `Debug`, `Display` and `std::error::Error`, carry
  the offending input or position where that helps, and convert into the error
  type consumers already use.

## Put constraints in types

- If a constraint is known at compile time (supported arity, bounded range,
  finite-only values, non-null), prefer const generics, sealed traits, newtypes
  with private fields, or bounded types over a runtime error or an assertion.
- Do not expose raw `f64`, tuples, `bool` or positional `a, b, c` parameters
  where a named type or error carries the meaning. A `bool` return that drops
  the failure reason needs a stated justification.
- Keep fields that uphold an invariant private; validate in the constructor.

## Record every deliberate C-compatibility choice

Keeping a C dependency, a C quirk, or an unusual signature "for compatibility"
is a design decision with a cost, not a default. For each one, write down in
the plan: what behavior it preserves, who observes it, what it costs (C
dependency kept, extra FFI crossing, unreachable code carried), and the
cheaper alternative. If a differential test shows the behaviors are
equivalent on supported inputs, prefer the pure-Rust version. If they differ,
raise the difference as a scoped finding with a recommendation instead of
silently choosing either side.

## Validate once, at the boundary

- Establish where inputs are validated. Once an entry point rejects or
  normalizes a value, delete downstream handling of that value instead of
  porting C's handling of it. Prove reachability from the actual callers.
- Tightening what a boundary accepts (rejecting malformed or non-finite input,
  trailing data, oversize input) is an observable change. Handle it as a
  compatibility finding with the evidence, a recommendation and a test that
  documents the old and new behavior; do not copy the C behavior only because
  C had it, and do not change it without that record.

## Use the repository's own test and benchmark tooling

- Use the property-test and benchmark libraries the workspace already depends
  on. A hand-written loop or custom benchmark `main` needs a recorded reason.
  A matched C-versus-Rust comparison is in addition to the repository's
  benchmark, not a replacement.
- Include worked examples in docs for codecs and formats (bytes, bit layout, a
  doctest), and the reason for each format limit.
- Test composition: several encoded units back to back in one buffer using the
  returned consumed length, not only single round trips.
- Turn the C-comparison corpus used during development into committed golden
  or property tests before the C implementation is removed. Evidence that
  exists only in logs or a scratch directory does not survive review.

## FFI shape and C cleanup

- When few C callers remain, simplify the C signature instead of mirroring it
  (sentinel or `Result`-like return rather than out-parameters, no
  always-success status codes, pointer types matching the real data). Record
  the change and update callers in the same scope.
- Rust callers call Rust directly; do not route Rust-to-Rust through a C
  symbol.
- Generated headers are generated by the repository's tool; never edit or
  duplicate them by hand. Put FFI in its own crate following the repository
  convention, not inside an unrelated entry-point crate.
- Delete replaced C sources, headers and build entries once consumers are
  moved. Do not leave stubs. For every exported symbol, list its callers at
  the starting SHA and export only symbols that are used.
- Bind C typedefs through the generated alias, never a hardcoded width, and
  check every preprocessor variant that changes the type.

## Delivery shape

- Prefer several reviewable steps over one large patch even when the scope is
  one coherent migration: add the Rust implementation with C still live, switch
  callers, then remove C and dependencies. Name the intended steps in the plan.
- Keep the patch in scope. Toolchain, lint, documentation or dependency-pin
  fixes for unrelated crates are separate, flagged changes.
- The exported patch must include new untracked files. Compare its file list
  with the reviewed files before handoff.
