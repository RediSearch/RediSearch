# FT.HYBRID execution with a variable number of workers

Design proposal, 2026-11-28. The implementation baseline is RediSearch master at `14a608df5b`. The target recovery model is the [coordinator head of pipeline ownership stack #11743](https://github.com/RediSearch/RediSearch/pull/11746), checked at its coordinator head `f19e6cbdb5`. Reply encoding follows [#11365](https://github.com/RediSearch/RediSearch/pull/11365), checked at `79e50a1b7a`. These are separate development heads. Their integration and the performance results below are proposed work.

## Objective and scope

Execute an ordered array of prepared subqueries with any positive number of available query workers. A single worker can finish a request even if no helper ever starts. Additional workers can run children concurrently. Preserve the existing inline RAM execution when the command runs with zero query workers or in a nonblocking context, its timeout fallback, and the existing disk restrictions in those contexts.

The production parser still accepts precisely the existing ordered SEARCH and VSIM pair, with the existing optional count of two. Syntax, error reporting, ranking and tie behavior, field precedence, profiles, RESP2/RESP3 replies, cursor mappings, and timeout policy come from the corresponding baseline. The executor consumes the existing request array and its count. An internal fixture can construct other counts for tests and benchmarks. Public limits, new source types, public cursor support, configuration knobs, and a generic task-graph framework are outside this change.

## Existing execution and reuse

| Path | Existing behavior on master | Change |
| --- | --- | --- |
| Standalone background | A search worker builds the pipelines, launches each safe depleter into a dedicated four-thread pool, and drives a merger which can wait for producer output. Early exits join outstanding jobs. | The build worker executes a child. Optional helpers use the query worker pool. Ready children feed the existing merger and tail. |
| Internal shard | Sub-cursors are reserved up front. The shard depletes the children, then publishes a cursor mapping. There is no shard fusion stage. | Use the same child scheduler with cursor publication as its continuation. Preserve reservation, publication and rollback. |
| Distributed coordinator | Each source reads through an RPNet. The coordinator submits depleters and then a tail to its own pool. Its FIFO assumption keeps a waiting tail behind its dependencies. | Arm all source streams, execute children on the coordinator pool, and make the normal tail runnable only when its dependencies are ready. Transport delivery stays on the I/O runtime. |
| Inline RAM | The main thread builds and executes synchronously with the established single spec read lock. | Drive the same logical order using the existing synchronous contexts and lock rules. Skip helper allocation, pool submission and blocked-client machinery. |

Keep existing AREQs, RP chains, fusion, sub-cursors, query limits, execution gates, reply-cycle arbitration, and row ownership helpers. Extract the operation that consumes one upstream into its producer buffer from the code that submits and waits for the work. Preserve its profiling and terminal status. Pool management belongs to the executor, and the RP remains the boundary through which a consumer or recovery reads the buffered output. ## Dispatch and normal execution

1. **Main-thread admission.** Establish the cycle with a stable list of child slots, owned command arguments, the configured timeout policy, and the construction-safe data needed to reply if the first worker never starts. Preserve the coordinator's lightweight request shell and deferred full parse. Keep the current weak spec reference while queued. Promote it when the build worker starts and handle a queued index drop through the existing error path. For a running request, the execution reference protects the spec's lifetime. See the separate read rules below.
2. **Prepare before exposing runnable work.** A single builder finishes the iterator, lookup, and RP topology. Give each background child its private Redis context for the selected DB. Set up producer domains for strict execution and wire their output mailboxes. For the coordinator, create and arm all per-source read iterators on their common I/O runtime. Publish the initialized tail context, reply slot, original budget, and immutable reply configuration under its gate **before making children claimable**. This splits publication from the first normal tail `Next`, which happen together on the stack today. Until publication the timeout callback can reply from the request shell. Once publication succeeds it can recover eligible children even if normal fusion has never run. A build that loses admission cleans up privately.
3. **Offer bounded parallelism.** The running builder is the first executor. With N children and a positive budget P on the selected pool, offer at most `min(N, P) − 1` helper tickets, using the existing query priority. Capture the budget from a safe configuration or executor snapshot. It is a scheduling hint. A failed optional submission releases its ticket and leaves the child available. Failure to dispatch the *initial* background request follows the existing request-error and unblock path. Publish all shared state before submitting any helper, since the helper may run immediately.
4. **Claim and execute.** Each worker claims one unclaimed ordinal under a short request-local mutex, obtains an execution lifetime reference, releases the mutex, and runs the complete child under its applicable ownership rules. Use the child's context, TLS for the current spec where required, error slot, limits and profile clock. On exit, release thread-affine locks and context bindings before running another child or the tail. Publish output and status before marking the normal dependency satisfied. Choose errors and construct replies using the existing source order and precedence. Completion order has no ranking significance.
5. **Run the ready continuation.** The worker that completes the final normal dependency claims the continuation once, leaves the scheduler critical section, and normally executes the tail inline under the tail's own admission. The shard continuation publishes cursors instead. A lost admission after strict timeout converts the worker's remaining duty to cleanup. A worker that finds only running siblings returns to its pool. The remaining workers own the progress obligation.

### State and lifetime

| Fact | Owner and allowed transitions |
| --- | --- |
| Which child can run | Scheduler mutex protects the next ordinal, claimed/finished accounting and single normal continuation claim. Typical child transitions are unclaimed → running → finished. Cancellation or fatal setup can close the unclaimed range in one operation. A skipped child never requires a queued helper to acknowledge it. |
| Which rows can be consumed | The producer's execution domain and existing output mailbox publish one coherent set of owned rows, status and diagnostics. Timeout recovery can publish it while the original worker is parked. Its late return only drops private resources and records actual job exit. |
| Who can produce a reply | Existing cycle arbitration and, under strict recovery, exclusive pipeline ownership. A continuation claim is permission to *attempt* admission. It does not authorize another reply. |
| When memory can be released | Keep a small ticket object with a lifetime-safe attachment to the live execution. Acquire an active reference while checking that attachment under the scheduler mutex. Detach it when the execution closes. A queued ticket can then return with only the small object alive. Active executors retain the request and their resources until they unwind. |

Construct one shared ticket object per background request that actually offers helpers. The pool can carry a reference to that object for each queued helper. Keep the scheduler bookkeeping at child boundaries and reuse indexed AREQ and mailbox storage. Give the builder a live reference through its final submission so a fast helper cannot destroy state under it. The terminal path owns one unblock after the builder, active borrowers and relevant transport cleanup are done. The Redis free callback releases cycle-owned resources on the required thread. A delayed empty helper cannot keep the request, reply bytes, disk view or blocked client alive. Bind tickets to a single cycle so a later cursor cycle cannot inherit stale work.

With one worker, the builder runs A, B, then the continuation. With two, the builder runs A and a helper can run B. Either can be last. With more children than workers, each finishing worker claims another child while work remains. Across several simultaneous commands, a pool full of builders is still a pool full of workers that can run children. These progress arguments assume the executor is serviced and external I/O eventually returns or is aborted. At a child boundary a worker may yield for fairness only after it has secured a runnable successor or another active runner owns the remaining work. Start with inline reuse and benchmark fairness before adding requeueing.

## Spec read lock and the common view

The spec reference, the spec RW lock, and the pipeline gate protect different things. The reference keeps an index alive. The RW lock protects index structures on the thread that takes it. The pipeline gate controls mutations to one query pipeline. Keep the scheduler mutex out of all three operations, Redis GIL acquisition, I/O, serialization and destruction.

| Execution mode | View and lock rule |
| --- | --- |
| Background RAM | Under one build-time spec read lock, read the maximum visible document ID once, copy it to every child **before** iterator construction, then construct all iterators against the protected trie and stats. Release the lock before launching or executing children. Each child acquires the read lock on its executing thread and revalidates as it does today. This includes a child running immediately on the builder's thread. |
| Disk | Open each child's query view and construct its iterators under the same build lock. Failure to open any view fails the build. Release the lock before depletion. Each view outlives its iterators and outstanding reads, including partial cursor and profile paths. |
| Inline RAM | Retain the existing same-thread read-lock scope and its suppression of intermediate unlocks. Reacquiring the writer-preferring lock recursively can deadlock with a queued writer. |
| Cluster | Apply the build boundary independently on each shard. The coordinator consumes published rows and cursor responses. It introduces no cluster-wide timestamp or spec lock. |

A later insert is outside every child's build-time bound, including when a helper starts much later. A later deletion or update can still affect visible results. An invalidated hybrid iterator can produce the existing retry error. On disk the storage layer defines the read-view contract and checks deletions against current state. Preserve the filtered KNN check before heap admission. Track the pending unfiltered KNN fix independently and test against the baseline revision actually used. Keeping a build lock until every child starts would reintroduce a dependency on queued workers and on writers holding the GIL. [Build and ID bound](https://github.com/RediSearch/RediSearch/blob/14a608df5b/src/hybrid/hybrid_exec.c#L934) · [Writer regression test](https://github.com/RediSearch/RediSearch/blob/14a608df5b/tests/pytests/test_hybrid_multithread.py#L115) · [Disk query-view contract](https://github.com/RediSearch/RediSearch/commit/fe721bd0b0) · [Unfiltered KNN follow-up](https://github.com/RediSearch/RediSearch/pull/12562)

## Timeout, Drain and cancellation

Use the execution domains from stack #11743, one per independent producer and one for the tail in blocked-client strict mode. Each domain has one mutable executor. Background admission checks the existing timeout, tries the gate and checks timeout again. A worker holds the gate through ordinary row processing. Before blocking on the GIL, a spec lock, transport, or storage, it commits consistent recovery state and releases the gate. On natural wake it must regain admission before touching shared state. Denied admission unwinds private resources, including any newly acquired external lock. Audit every surviving frame, including Rust borrows, temporary result limits and profile counters. Keep all gates unnested. The scheduler adds no per-row locks, atomics or reference operations. [Ownership contract](https://github.com/RediSearch/RediSearch/blob/f19e6cbdb5/docs/design/pipeline-execution-ownership.md) · [Gate implementation](https://github.com/RediSearch/RediSearch/blob/f19e6cbdb5/src/pipeline_execution.c)

**Strict timeout sequence**

1. On the main thread, mark the parent and children timed out before attempting recovery. The existing timeout flag closes future admissions. The callback has no dependency on the ticket queue, a child count reaching zero, or a worker acknowledging cancellation.
2. Enter the tail gate and inspect its publication. Before publication, send the established empty timeout response using construction-safe metadata. After publication, exclude further tail execution and capture whether recovery is needed. Release the gate. Completed EOF and fatal-error paths retain their existing precedence.
3. When needed, enter each producer domain independently and recover its eligible buffered state through the stack's depleter recovery. Publish its output and diagnostics exactly once. An unstarted but fully constructed producer can contribute whatever its upstream Drain can already provide. A parked producer needs no wakeup. An unpublished or unavailable upstream can contribute zero rows.
4. Reenter the tail domain. Drain through its final RP, respecting the stack's accumulator rules. A nonempty accumulator yields its own available output. An initially empty accumulator may recover eligible upstream Drain output. The merger keeps each child's rank and window progress and yields the committed union. Safe loaders only expose fully loaded rows. RPNet may consume a finite set of already available replies. It neither sends a cursor read nor waits for another batch during Drain. Serialize only eligible rows and published diagnostics. Wake transport channels as needed for subsequent worker cleanup.

The main thread acquires a mutex in `PipelineExecution_RunDrain`. A worker parked on an external lock releases that mutex before parking. An actively executing worker can delay takeover until it reaches a safe release point. Drain and encoding also take time proportional to eligible output. Measure active-section delay separately from reply-to-worker-exit time. The strict callback must complete in a test that holds a parked worker indefinitely. [Hybrid recovery order](https://github.com/RediSearch/RediSearch/blob/f19e6cbdb5/src/hybrid/hybrid_exec.c#L793) · [Coordinator recovery](https://github.com/RediSearch/RediSearch/blob/f19e6cbdb5/src/coord/hybrid/dist_hybrid.c#L1307)

| Other event | Required action |
| --- | --- |
| RETURN timeout | Stop further normal work once its deadline is observed. Each executing chain fully unwinds Next before sequential Drain on the owning thread. Account for unclaimed work without queueing it solely to observe timeout. Recover eligible output and preserve warning, cursor continuation and original chunk budget. Retain the existing per-command deadline across all child claims. |
| FAIL timeout | Reply with the timeout error and discard row output. Signal cancellation and let active workers release private resources. Cleanup never invokes Drain. |
| Disconnect | Suppress client output, stop new work, abort pending transport waits, dispose unpublished cursors and release all execution references. Use the existing once-only unblock path. |
| OOM or fatal child error | Carry the actual stop cause, warnings and child diagnostics through the selected policy. Keep a retryable index change distinguishable from a timeout. Retire unstarted work only if doing so preserves established error precedence. |
| Initial internal shard cursor response | Keep its mapping protocol and policy-specific publication/rollback, including the strict timeout response with zero cursor IDs. Generic tail row Drain does not replace this control response. A later cursor read gets its own reply cycle. |

## Reply-buffer integration

Use #11365's cycle-owned Redis buffer and shared row serializer. Producers publish intermediate rows needed for fusion. The tail alone writes final rows during ordinary execution. Publish the buffer slot, committed row count, original limit, schema/framing state and reply metadata with the tail context. Keep a complete row, its count and any framing update within the same admitted execution segment. A yielding boundary must expose a complete prefix. If a serializer needs a blocking operation mid-element, finish private staging before committing the complete element under ownership. This is an integration requirement to verify on the combined heads.

After strict takeover, the recovery owner resumes from the published prefix, appends only eligible Drain rows within the remaining original limit, then finalizes and moves the buffer once through the cycle's winning reply path. Preserve OFFSET progress, RESP framing, errors, warnings and profiles. The losing worker cannot append or reset the recovered buffer. FAIL can discard the entire buffer, including after a late runtime error. Create/free buffers using the required Redis context and thread affinity. Keep request teardown behind the final active borrower even when the client received its response earlier. [Reply-buffer design](https://github.com/RediSearch/RediSearch/blob/79e50a1b7a/docs/design/reply-buffer-integration.md)

## Differences from the initial ticket proposal

| Original idea | Design decision and reason |
| --- | --- |
| Size the request from the count on arrival and make it thread-safe. | Size the shell on arrival. Publish the completed plan after build. Each mutable pipeline has one execution owner. Only scheduling, producer publication and the reply handoff cross threads. |
| Submit tickets for the available subtasks. | A ticket is an opportunity to claim any ready child. Count the builder as one runner and bound helpers by available parallelism. A saturated pool incurs at most one optional helper per normal two-source request. |
| Have a worker take the next subtask after completing one. | Adopt this at child boundaries. A worker finding only active siblings returns immediately. Its lifetime and per-thread lock state are explicit before reuse. |
| Queue the tail or run it on the worker that completes the last child. | Default to inline execution on the last finisher. Publish the tail for recovery early. Normal tail readiness and timeout takeover are independent. The shard uses a cursor-publication continuation. |
| Extra tickets exit quickly once work is gone. | Require stale tickets to retain only a small detached handle. Separate recoverable output, real job exit and the single client reply so a stale ticket cannot touch freed query state or prolong a large request. |
| Use available parallelism while keeping spec reads consistent. | Preserve one common build-time visibility boundary and the existing per-child revalidation/storage views. This permits a writer to finish between child claims and avoids cross-thread lock handoff. |

Starting the normal merge after every child finishes can lose today's overlap between merging one source and depleting another. Early tail publication preserves the *ability* to recover under strict timeout. Validate the actual partial results against the ownership-stack baseline at controlled checkpoints. If correctness or measured latency/peak memory warrants it, allow a single admitted tail owner to accumulate already-published sources and return when none are ready. Keep ranks, windows and deterministic field selection by source ordinal. Add this optimization only with evidence and keep the final reply continuation unique.

| 6. Remove obsolete waits and evaluate performance | Remove dedicated depleter pool setup/teardown and hybrid FIFO/join dependencies once all callers migrate. Deterministic cases for acceptance:

- Run 2 and 8 prepared children with one worker and `TIMEOUT 0`. Park all helper tickets until after reply and heavy-state release. Assert one claim per executed child, a single normal continuation, and one unblock. Repeat with several commands saturating the pool and with helper queue submission failure. Exercise helper-first execution, reordered completions, late no-ops and supported pool resizing while work is in flight.
- Park after build and between two child claims. Insert, delete or reindex matching documents, force numeric-tree revalidation, and exercise filtered and unfiltered KNN. Check late-ID exclusion, established deletion/error behavior, and writer progress. Exercise an index drop while queued, disk view-open failure and outstanding disk reads during cleanup.
- Force strict timeout before build, between publication and the first claim, with one producer finished and another queued, and with a producer parked on spec acquisition, GIL or shard I/O. Keep the parked worker suspended until the reply is read. Compare just the eligible prefix, warnings and published profiles against deterministic #11743 fixtures. Resume the worker and verify exactly-once disposal.
- Time out after serializing a prefix, at an external wait, and after tail completion before reply. Exercise RETURN, FAIL, strict, a runtime error after rows, disconnect, and parent- and child-originated memory stops. Check ordering, count, offsets, remaining limit and valid RESP2/RESP3 framing. Exercise ownership transfer and late cleanup under sanitizers.
- For shards, inject failure after partial cursor reservation and timeout on both sides of mapping publication. For the coordinator, exercise one slow shard, all shards stalled, disconnect with no subsequent reply, and late transport delivery. Check stable mapping shape and that cursor counts, view counts, blocked clients and live buffers return to baseline.

## Performance plan and decision criteria

Run three comparisons. First A/A to establish noise. Then compare the old and new executor on identical dependency revisions, build flags, CPU affinity/quota, data, index parameters and Redis configuration. Finally measure the complete integration against master to show the combined user-visible effect. Record actual runnable pools and CPU: today `WORKERS 1` also has a four-thread depleter pool. Run one-worker and two-worker cases first. Report both equal configured worker count and equal process CPU budget.

| Workload | Runs and purpose |
| --- | --- |
| Public pair | Reuse the existing arXiv RRF/LINEAR macro workloads. Run RAM standalone and a three-shard coordinator, with 1, 2, 4 and 8 query workers plus an inline RAM control. Measure single-client latency, a concurrency sweep through saturation, and fixed offered rates below and around the throughput knee. Include a supported disk configuration. |
| Internal scaling | Construct N = 2, 4, 8, 16 via the fixture. Use cheap children to expose ticket overhead, balanced expensive children for parallel speedup, and one slow child to measure tail delay. Use overlapping and disjoint windows and short versus large replies. Measure build-lock hold time as N increases. |
| Mixed traffic | Mix expensive hybrid requests with ordinary short searches and writes on the same index. Vary load and capture each traffic class's p99. Compare inline reuse with a child-boundary fairness variant only if short requests suffer. |
| Timeout and cancellation | Run all timeout policies with controlled slow input, large serialized results, parked workers and disconnects. Report successful throughput, timeout rate and eligible rows returned as separate quantities. |

Record p50/p95/p99 latency, throughput at a fixed p99, CPU time per successful query, peak memory, and counts of successes, errors and timeouts. With benchmark-only sampling, break latency into build, queue, producer, tail and reply. Record helpers offered/used/stale, mailbox bytes, spec/GIL waits, strict callback latency, and time from reply to resource release. Capture latency distributions for writes and ordinary searches independently. Warm the dataset, interleave repeated A/B runs and retain raw histograms and revision/configuration manifests. Predeclare acceptable regressions from the A/A noise and service targets before interpreting the candidate. [Existing benchmark workload](https://github.com/RediSearch/RediSearch/blob/14a608df5b/tests/benchmarks/hybrid-arxiv-titles-384-angular-rrf-text-vector.yml)

Correctness and liveness are release gates. For performance, judge one-worker CPU/query and loaded throughput together with isolated latency, fairness, memory and strict reply latency. A reproducible loss outside the agreed band needs attribution and an explicit trade-off decision. Measure the impact of helper queue churn before considering a pool-level enqueue-if-idle primitive. Evaluate early merge accumulation first if the regression tracks skewed branches or high buffered memory.
